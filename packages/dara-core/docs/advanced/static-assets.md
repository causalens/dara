---
title: Static assets
---

Use static assets for files such as images, fonts and downloadable documents that your application serves unchanged.

## Application files

Dara automatically includes the `static/` directory in the application root. For example:

```text
my-app/
├── pyproject.toml
├── my_app/
│   └── main.py
└── static/
    ├── logo.svg
    └── documents/
        └── guide.pdf
```

These files are available at `/static/logo.svg` and `/static/documents/guide.pdf`. Subdirectories retain their names. When the application is mounted under a base URL such as `/dashboard`, the URLs become `/dashboard/static/logo.svg` and `/dashboard/static/documents/guide.pdf`.

To include another directory, register it on your configuration builder:

```python
from dara.core import ConfigurationBuilder

config = ConfigurationBuilder()
config.add_static_folder('./public_assets')
```

Relative paths are resolved from the application root when you run Dara there. The registered directory must exist during development and builds. Its contents share the same `/static/` URL root: `public_assets/icons/help.svg` is served at `/static/icons/help.svg`, without a `public_assets` prefix. Registering extra folders does not disable automatic inclusion of `static/`.

## Development and production

`dara dev` serves registered files directly from their source directories. It watches them for additions, changes and deletions without restarting Python. Refresh the page to see an updated image or document; static files do not receive React HMR. If you create the application's `static/` directory after starting development, restart `dara dev` so it is discovered.

`dara build` copies static assets into the built output. `dara start` serves that output, so rebuild after changing assets. Startup checks available registered asset sources against the build and reports stale output if they differ.

Deploy the complete `dist/` directory, including hidden files. A runtime deployment can omit the frontend source checkout and serve the built assets with Python alone. If source files remain in the deployment, keep them consistent with the build.

## Conflicting paths

Every asset needs a unique output path. For example, `static/logo.svg` and `public_assets/logo.svg` conflict when both folders are included. Dara reports an error instead of choosing which file wins. Rename a file, put it in a subdirectory, or remove the duplicate registration. During development, serving resumes after the conflict is fixed.

Package assets occupy `/static/<python-module>/`. Application folders cannot overwrite these package namespaces or files generated by Dara and Vite, such as the application HTML. Keep application assets under distinct paths.

## Changes from Dara 1.x

`config.add_static_folder(...)` and existing asset URLs remain supported. Files are now served from their original directories during development and copied into the production output during `dara build`; Dara does not move them into your application's `static/` directory. Conflicting destinations produce errors rather than overwriting another asset.

JavaScript component implementations and global styles use module imports through the new frontend pipeline. Static registration serves files; it does not inject script or stylesheet tags. See the [Dara 2.0 migration guide](../dara-2-migration.md) for the source and command changes.
