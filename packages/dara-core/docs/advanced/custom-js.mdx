title: Custom JavaScript Components
---

Dara uses Vite for both development and production. Every registered Python component or action points at one JavaScript module, and that module's default export implements it. Local files and published packages work the same way.

## Prepare an application

Install Node >=22.12.0 and pnpm 12, then run `dara dev` from the app root in your Python environment. Dara checks for these tools but does not install them. Generated apps include a `mise.toml` with the versions pinned, so `mise install` sets them up for you.

The app declares its Python configuration explicitly:

```toml title=pyproject.toml
[tool.dara]
config = "my_app.main:config"
```

`dara dev` creates any missing `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `vite.config.ts`, `tsconfig.json` and `js/index.tsx`. Commit them along with the lockfile.

These files belong to your application. Later runs only reconcile Dara's own dependencies; your configuration is left alone.

```ts title=vite.config.ts
import dara from '@darajs/vite-plugin';
import { defineConfig } from 'vite';

export default defineConfig({ plugins: [dara()] });
```

`dara dev` runs Python reload, Vite and TypeScript together, all served from the Python server's origin. React edits apply through HMR, and changing a Python registration regenerates the imports. Type errors show up as development diagnostics, and they fail production builds.

A few flags help with IDE setups:

- `--no-reload` runs Python in the current process, so you can attach a debugger.
- `--frontend-only` and `--backend-only` split the two halves across separate sessions.

## A local component

Place application JavaScript under `js/` and point `js_source` directly to its implementation:

```python title=my_app/gauge.py
from typing import ClassVar
from dara.core.definitions import ComponentInstance

class Gauge(ComponentInstance):
    js_source: ClassVar[str] = './js/gauge.tsx'
    value: float
```

```tsx title=js/gauge.tsx
export default function Gauge({ value }: { value: number }) {
  return <meter min={0} max={100} value={value}>{value}</meter>;
}
```

Import and use `Gauge` in your Python pages like any built-in component; import discovery registers it for you. For classes that are only imported dynamically, call `config.add_component(Gauge)`.

A local `js_source` path must start with `./js/` and cannot point outside that directory. The default export can have any JavaScript name — the component's Python identity is what matters.

Add your own dependencies with `pnpm add`. Dara's own dependencies live in the `dara` catalog in `pnpm-workspace.yaml`, and `dara lock` brings them back in line after you change Python packages. Use `dara dev --frozen` to report drift instead of fixing it.

## Variables and actions in a component

The `useVariable` and `useAction` hooks decode Dara's serialized props. `useVariable` subscribes to updates and gives you a setter; `useAction` gives you an event handler and a running flag.

```tsx title=js/counter.tsx
import { useAction, useVariable } from '@darajs/core';
import type { Action, Variable } from '@darajs/core';

interface CounterProps {
  value: Variable<number>;
  onclick: Action;
}

export default function Counter(props: CounterProps) {
  const [value, setValue] = useVariable(props.value);
  const [onClick, running] = useAction(props.onclick);
  return (
    <div>
      <button onClick={() => setValue(value + 1)}>{value}</button>
      <button disabled={running} onClick={onClick}>Run action</button>
    </div>
  );
}
```

## A custom action

Actions use the same module contract:

```python
from typing import ClassVar
from dara.core.base_definitions import ActionImpl

class VisitCountry(ActionImpl):
    js_source: ClassVar[str] = './js/visit-country.ts'
    country: str
```

```ts title=js/visit-country.ts
import type { ActionHandler, ActionImpl } from '@darajs/core';

interface VisitCountry extends ActionImpl {
  country: string;
}

const visitCountry: ActionHandler<VisitCountry> = (ctx, action) => {
  ctx.navigate(`/country/${encodeURIComponent(action.country)}`);
};
export default visitCountry;
```

Use `VisitCountry(country='United Kingdom')` as a button's `onclick`. Import discovery finds action classes too; call `config.add_action(VisitCountry)` when you need to register one explicitly.

To do server work first, override `execute` in Python and call `await super().execute(ctx)` to hand the action to the browser.

## Application and package setup

`js/index.tsx` is your application's setup module. Import global CSS and do app initialization there. It is not a registry of component exports — you never list your components in it.

A library registered with `config.add_module_dependency('my_python_package', '@example/widgets')` does the same thing through a `./setup` npm export. Either way, setup runs once, as a normal module import.

Your Vite configuration can add plugins and aliases as usual. Dara owns the generated entry module, the HTML, where output is published and its own server endpoints.

Dara decides whether a build is still fresh by hashing everything the build reads. It cannot see files a plugin opens by itself, so declare those:

```ts
plugins: [dara({
  inputs: ['build/banner.txt'],
  directories: ['build/templates'],
  environment: ['VITE_PRODUCT_VARIANT'],
})]
```

- `inputs` — individual files your plugins read. Each file's contents are hashed into the build.
- `directories` — directories read the same way. Every file underneath is hashed, so adding, editing or removing one makes the build stale.
- `environment` — names of environment variables the build reads. A changed value makes the build stale.

Paths are relative to the app root. If you leave something undeclared, `dara start` will serve a build that no longer matches its sources.

## Workspaces and published libraries

To ship components in a package, point `js_source` at an npm subpath such as `'@example/widgets/gauge'`. Dara takes the npm package name from `js_source` and finds the matching Python distribution from the module that declared it, then requires the npm version that matches the installed Python version.

Apps in one workspace share a Dara version, the `dara` catalog and the root pnpm lockfile, but each keeps its own development state.

A library checkout can expose source for Dara and compiled output for ordinary consumers:

```json title=package.json
{
  "name": "@example/widgets",
  "exports": {
    "./gauge": {
      "dara-source": "./js/gauge.tsx",
      "types": "./dist-lib/gauge.d.ts",
      "default": "./dist-lib/gauge.js"
    }
  },
  "publishConfig": {
    "exports": {
      "./gauge": {
        "types": "./dist-lib/gauge.d.ts",
        "default": "./dist-lib/gauge.js"
      }
    }
  },
  "files": ["dist-lib"]
}
```

Both Vite and TypeScript resolve the `dara-source` condition, so an app in the workspace compiles the library's source under its own settings while published consumers get `dist-lib`.

A few rules apply to source exports:

- Wildcard exports need a dedicated source directory, such as `./js/*.tsx`. Exact exports can sit at the package root.
- Use relative imports inside the library.

Development never builds sibling libraries. `dara build` builds reachable workspace dependencies in pnpm order; pass `--no-deps-build` if your repository has already built them.

A package can be both a library and a Dara app. Keep `vite.config.ts` and `tsconfig.json` for the app, and add `vite.lib.config.ts` and `tsconfig.lib.json` for publication. The two outputs must not overlap — use `dist/` for the app and `dist-lib/` for the library. The app can import the library by its own npm name without depending on itself.

When you build the library, externalize React and its runtime subpaths and emit declarations. Publish with pnpm so `publishConfig.exports` replaces the source condition in the packed manifest.

Before releasing, install the real `pnpm pack` tarball into a clean consumer and check that public imports resolve to compiled files even when `dara-source` is enabled.

## Static assets

For application files and `config.add_static_folder(...)`, see [Static assets](./static-assets.md).

Your application's `static/` files are served at `/static/`. A Python package's assets are served at `/static/<python-module>/`, and it registers them through the `dara_assets` entry point:

```python
asset_manifest = AssetManifest(
    base_path=Path(__file__).parent,
    static_assets=[StaticAsset(source='common', target='.')],
)
```

Paths are relative to `base_path` and cannot escape the package's namespace. These URLs are the same in development and production, including apps mounted under a base URL.

Static assets are for real files you want served as-is, such as a vendored plotting library that a component loads at runtime. JavaScript that is part of your app belongs in a module import instead — there is no script ordering to configure.

During development Dara watches the static roots. If two packages claim the same destination you get a diagnostic, and serving resumes once you fix the collision.

## Build and deploy

`dara check --json` reports diagnostics without changing anything.

`dara build` type-checks and produces `dist/`, then `dara start` serves it. Build never repairs dependency drift, so commit your dependency files first. Start always runs in deployment posture; opt into API docs with `--api-docs`.

Deploy the whole output directory, including its private `.dara-build.json` marker. On startup Dara checks the registered contract, the output hashes and any build inputs it can still see — no JavaScript tooling required.

A runtime image can contain just Python and the compiled output; you can leave the frontend checkout out entirely. If you do ship the sources, they have to match the build. And if anything changes while a build is running, Dara discards it and keeps the previous output.
