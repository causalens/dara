title: Custom JavaScript Components
---

Dara uses Vite for both development and production. Every registered Python component or action names one JavaScript module whose default export implements it. Local files and published packages follow the same contract.

## Prepare an application

Install Node >=22.12.0 and pnpm 12, then run `dara dev` in your Python environment from the app root. Generated apps include optional `mise.toml` pins; `mise install` installs those tools. Dara checks the toolchain but does not install it.

The app declares its Python configuration explicitly:

```toml title=pyproject.toml
[tool.dara]
config = "my_app.main:config"
```

`dara dev` prepares missing `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `vite.config.ts`, `tsconfig.json` and `js/index.tsx` files. Commit the project files and lockfile. These files belong to your application; subsequent preparation reconciles Dara dependencies without replacing your configuration.

```ts title=vite.config.ts
import dara from '@darajs/vite-plugin';
import { defineConfig } from 'vite';

export default defineConfig({ plugins: [dara()] });
```

The single development command supervises Python reload, Vite and TypeScript behind the Python server's origin. React edits update through HMR; Python registration changes regenerate imports. `dara dev --no-reload` runs Python in the current process for IDE debugging. `--frontend-only` and `--backend-only` support split IDE sessions. Type errors appear in development diagnostics and fail production builds.

## A local component

Place application JavaScript under `js/` and point `js_source` directly to its implementation:

```python title=my_app/gauge.py
from typing import ClassVar
from dara.core.definitions import ComponentInstance

class Gauge(ComponentInstance):
    js_source: ClassVar[str] = './js/gauge.tsx'
    value: float
```

```tsx title=js/gauge.tsx
export default function Gauge({ value }: { value: number }) {
  return <meter min={0} max={100} value={value}>{value}</meter>;
}
```

Import and use `Gauge` in your Python pages as any built-in component. Existing import discovery registers it. For dynamically imported classes, use `config.add_component(Gauge)`. A barrel export and a `local=True` flag are unnecessary. A local path must start with `./js/` and cannot escape that directory. The default export can have any JavaScript name; Python's component identity remains unchanged.

Add normal application dependencies with `pnpm add`. Dara-managed dependencies use the `dara` catalog in `pnpm-workspace.yaml`; `dara lock` reconciles them after Python package changes. `dara dev --frozen` reports drift without repairing checked-in files.

## Variables and actions in a component

The existing `useVariable` and `useAction` hooks decode Dara's serialized props. `useVariable` subscribes to updates and supplies a setter. `useAction` supplies an event handler and a running state.

```tsx title=js/counter.tsx
import { useAction, useVariable } from '@darajs/core';
import type { Action, Variable } from '@darajs/core';

interface CounterProps {
  value: Variable<number>;
  onclick: Action;
}

export default function Counter(props: CounterProps) {
  const [value, setValue] = useVariable(props.value);
  const [onClick, running] = useAction(props.onclick);
  return (
    <div>
      <button onClick={() => setValue(value + 1)}>{value}</button>
      <button disabled={running} onClick={onClick}>Run action</button>
    </div>
  );
}
```

## A custom action

Actions use the same module contract:

```python
from typing import ClassVar
from dara.core.base_definitions import ActionImpl

class VisitCountry(ActionImpl):
    js_source: ClassVar[str] = './js/visit-country.ts'
    country: str
```

```ts title=js/visit-country.ts
import type { ActionHandler, ActionImpl } from '@darajs/core';

interface VisitCountry extends ActionImpl {
  country: string;
}

const visitCountry: ActionHandler<VisitCountry> = (ctx, action) => {
  ctx.navigate(`/country/${encodeURIComponent(action.country)}`);
};
export default visitCountry;
```

Use `VisitCountry(country='United Kingdom')` as a button's `onclick`. Import discovery handles action classes; use `config.add_action(VisitCountry)` when explicit registration is needed. An optional Python `execute` override can perform server work and call `await super().execute(ctx)` to send the action to the browser.

## Application and package setup

`js/index.tsx` is the application setup module. Import global CSS or perform app initialization there; it is not a registry of component exports. A library registered with `config.add_module_dependency('my_python_package', '@example/widgets')` provides an explicit `./setup` npm export. Setup runs once through normal module imports. Keep setup modules separate from component barrels.

Vite configuration can add normal plugins and aliases. Dara owns the generated entry, HTML, output publication and internal server endpoints. A plugin that reads extra files or environment values must declare them so build freshness can be checked:

```ts
plugins: [dara({
  inputs: ['build/banner.txt'],
  directories: ['build/templates'],
  environment: ['VITE_PRODUCT_VARIANT'],
})]
```

## Workspaces and published libraries

A package implementation uses an npm subpath, for example `js_source = '@example/widgets/gauge'`. The npm name comes from `js_source`; the Python module identifies its installed distribution. The installed Python version determines the npm requirement. All Dara apps in a workspace use the same Dara version, catalog and root pnpm lockfile. Each app has separate development state.

A library checkout can expose source for Dara and compiled output for ordinary consumers:

```json title=package.json
{
  "name": "@example/widgets",
  "exports": {
    "./gauge": {
      "dara-source": "./js/gauge.tsx",
      "types": "./dist-lib/gauge.d.ts",
      "default": "./dist-lib/gauge.js"
    }
  },
  "publishConfig": {
    "exports": {
      "./gauge": {
        "types": "./dist-lib/gauge.d.ts",
        "default": "./dist-lib/gauge.js"
      }
    }
  },
  "files": ["dist-lib"]
}
```

Both Vite and TypeScript resolve `dara-source`. Wildcard source exports use a dedicated source directory, such as `./js/*.tsx`; exact source exports may live at the package root. Use relative internal imports and compile source under the consuming app's settings. Development does not build sibling libraries. Production builds reachable workspace dependencies in pnpm order; use `dara build --no-deps-build` when the repository has already built them.

A package that is also a Dara app keeps `vite.config.ts` and `tsconfig.json` for the app, and separate `vite.lib.config.ts` and `tsconfig.lib.json` files for publication. Outputs must not overlap: use `dist/` for the app and `dist-lib/` for the library. npm self-references work in the library's own app without a dependency on itself.

Externalize React and its runtime subpaths from library bundles, and emit declarations. Publish using pnpm so `publishConfig.exports` replaces the source condition in the packed manifest. Install the actual `pnpm pack` tarball into a clean consumer and verify public imports resolve to compiled files even with `dara-source` enabled. Python wheels contain Python code and genuine static assets; they no longer contain generated UMD libraries.

## Static assets

For application files and `config.add_static_folder(...)`, see [Static assets](./static-assets.md).

Application `static/` files are served at `/static/`. Package assets use `/static/<python-module>/`. Register them through the existing `dara_assets` entry point using `AssetManifest(base_path=..., static_assets=[StaticAsset(source='common', target='.')])`. File paths are relative to `base_path` and cannot escape their namespace. Assets retain their URLs across development and production, including applications mounted under a base URL.

Script ordering and generated library tags are replaced by module imports. Genuine vendored files such as plotting libraries remain static assets and are loaded by their components. Development watches static roots; conflicting destinations produce a diagnostic and resume serving after the collision is fixed.

## Build and deploy

Run `dara check --json` for read-only diagnostics. Run `dara build` with committed dependency files to type-check and produce `dist/`, then `dara start` to serve it. Build never repairs dependency drift. Start always uses deployment posture, with API docs opt-in via `--api-docs`.

Keep the complete output, including its private `.dara-build.json` marker. Startup validates the registered contract, output hashes and any available build inputs without JavaScript tools. A runtime image can contain only Python and compiled output, omitting the frontend checkout as a whole. If frontend sources remain, they must still match the build. Changes during compilation reject staging and preserve the previous output.
